# 可追溯开发协作

建立可核对的关联：需求来源 → Task → 实现与审查证据 → Git 提交 → 集成结果。用最少文档回答：为什么做、谁在做、依赖什么、何时交付、如何验收、现在能开始哪些任务。

## 使用边界

- 先读取项目现有约定、计划和任务记录，沿用已有目录、编号与工作流。小任务复用现有记录，不强制新建整套文档。
- 用户只要求规划时，完成规划；用户要求执行时，在已有授权内推进。计划里列出的部署、推送、创建对话或自动续跑，不等于已获得执行授权。
- 项目约束写进项目计划。不要把某个案例的模型、平台、技术栈、专家人数、工期或数据库规则固化为通用规则。模型与推理强度按全局配置分配；全局未指定的项继承当前主控的实际运行配置。本 skill 不按角色或阶段另设模型限制。
- 只询问会影响范围、业务取舍、依赖或执行权限且无法从资料确定的问题。普通格式与实现细节自行选择最小可行方案。
- 默认使用当前会话主控模式。用户明确选择阶段会话模式时，按下文区分“总控”和“阶段负责人”；仅编写该模式的计划或修改 skill，不构成创建会话、发送消息或启动业务执行的授权。

## 1. 文档与需求规则

- 只维护一份主计划作为范围、任务状态、分工和排期的权威记录。复杂任务可有独立任务卡与证据文件，主计划链接它们，避免重复维护同一字段。
- 本期必做、明确后置、验收环境、外部依赖和交付期限要清楚。区分用户要求、已确认决定、建议和待确认事项。
- 为需跨任务追踪的需求分配稳定编号，如 R01；Task 使用稳定编号，如 T001。拆分后保留父子关系，取消后保留记录，不重排或复用旧编号。
- 每个 Task 链接需求来源；每个本期需求都有实施任务和验收去向，或明确标为后置、取消、待确认。跨 Task 的需求或业务结果，须核对其全部必需场景在约定集成版本中的验收结论，并链接总体结论与证据；分项 Task 完成不能单独证明整体完成。
- 写具体动作与结果，避免“完善功能”“优化体验”等无法验收的表述。日期写明年份，排期注明时区、工作日口径及估算假设。
- 规划和验收均按相关端、角色及使用场景列清范围，避免以一个入口的成功代替完整功能交付。

创建或调整文档时，按需读取 [最小文档模板](references/templates.md)，只使用当前任务所需部分。

## 2. Task 拆分与开始条件

一个 Task 对应一个可审查结果，并有唯一交付负责人。多人参与时明确各自职责及最终集成负责人。按结果、依赖或冲突边界拆分，不按文件数量机械拆分，不设统一强制时长。

每个 Task 按适用范围和所处阶段记录以下信息。规划阶段记录已知信息与必要待定项；实际日期、提交和验收结果随执行补齐。不适用项可省略，有歧义时注明原因；适用的安全、权限、数据及必要验收要求不能据此省略。

- 目标、需求来源、本期范围及交付物。
- 负责人、修改范围、共享文件与接口约定。
- 前置 Task、所需成果以及依赖完成的判定条件；无依赖也明确写明。分阶段任务分开记录「当前场景实施准入」与「最终冻结／签收条件」，引用准确可用成果，不把整个上游最终完成误作每个小场景的开始条件。
- 验收场景、环境和证据要求；适用时包括失败路径、权限、数据一致性和 UI 检查。
- 估算、计划日期、实际开始与结束、状态、阻塞及下一步。
- 分支或工作目录、实现提交、审查结果、集成提交或目标分支中的对应记录。

开始开发必须同时满足：目标和验收可执行、负责人和环境可用、全部前置条件满足、修改范围没有未解决的并发冲突。仅任务名称或计划日期齐全，不足以认定已就绪。

## 3. 依赖与并行规则

### 主流程与责任

- 在唯一主计划中明确用户可见的端到端结果、最近验收点和当前阻塞。主流程可跨多个端和 Task，不按技术层或文件机械拆开连续闭环。
- 默认由主控推进任务，并对主计划、集成、依赖放行和交付结论负责。开发、测试、修复和写入分工遵循全局规则及已有授权，模型配置遵循“使用边界”。为满足规定配置或验收约定而串行委派测试，不受普通并行任务数量条件限制；委派不扩大执行权限。
- 优先解除影响当前验收的阻塞，再处理可后置优化；不得省略权限、数据正确性或约定的必要检查，也不把所有边缘问题列为开工前置条件。

### 可选：阶段会话串行执行

用户要求各阶段由独立 Codex App 会话完成开发、测试和验收时，先读[阶段会话模式](references/stage-sessions.md)。总控维护主计划、阶段准入和最终签收；阶段负责人在授权范围内连续完成阶段工作。该模式在同一检出目录和当前分支上串行交接写入职责，不允许多个会话同时写入；普通并行支线仍使用隔离规则。阶段报告须经总控核对实际文件和证据后才计为完成，不因会话结束自动放行下一阶段。

### 依赖与放行

- 有跨任务依赖时记录依赖关系，检查缺失编号、自依赖和循环；复杂关系可画图。发现循环时调整任务边界或抽出共同前置成果，不带着循环排期。
- 依赖按约定成果判定：所需成果已验收，并可在约定分支或版本中使用，才放行对应场景；没有明确阶段成果时，默认等待整个前置 Task 完成。多个前置条件须全部满足，提交代码或发起审查不能自动解除依赖。
- 硬依赖未满足时，只能推进与它无关且已明确范围的准备工作。契约可作为阶段成果或独立任务先交付；完整联调仍须等待全部必需成果，不能用拆分绕过真实依赖。
- 前置任务取消或被替代时，先确认所需成果去向并修订依赖，不能视为完成。任务完成、集成、阻塞或重新打开后，重新判定受影响任务是否就绪；不兼容变更须复查下游，旧证据不能继续作为放行依据。

### 并行与交接

- 仅在已获授权、环境支持且符合全局分工条件时并行。任务须有独立可验收的交付边界、已满足的依赖、可用执行资源，以及不冲突的修改范围和运行环境。已就绪不等于必须并行，分工收益应覆盖交接与集成成本。
- 位于关键路径或被当前验收等待，不单独构成禁止委派的理由。按既定职责评估执行者、交付时间、资源冲突，以及主控能否同时推进其他必要工作；不能借此绕过全局修复职责或并行准入要求。
- 只读任务明确禁止写入，无须为此新建分支或工作目录。已获授权的并行写入使用隔离的工作目录及分支，明确共享文件、接口和迁移的唯一修改负责人；共享服务、账号和数据仍须单独检查冲突。共享环境中的迁移和部署串行进行。
- 任务出现新依赖或成为阻塞时，依据现有成果、剩余工作、交付预期和交接成本决定继续执行、缩小范围或接手，不因成为阻塞自动换人。确需接手时，先确认原执行者停止相关修改并核对成果；修复等执行职责仍遵循全局规则。
- 主控在约定检查点核对成果、必要验证与集成证据，再按依赖条件放行。普通支线执行者不直接修改主计划或共享目标分支；已启用阶段会话模式时，按该模式的交接规则限定指定检出目录的当前写入者和范围。计划中的派发、集成和完成不能当作实际状态。

涉及共享服务、登录态、用户实时配合或会破坏现场的验收时，操作前读取[现场协作](references/onsite-coordination.md)。实际委派时读取[派发与结果记录](references/coordination.md)；仅使用 Codex App 多对话协作时读取其中的工具操作部分。

## 4. 排期规则

- 区分工作量、持续时间和自然日。估算包含实现、必要验证、审查、修复及集成，明确谁承担主协调与验收工作。
- 按依赖链和负责人可用时间排期；识别决定最终交付日期的最长依赖链。并行数量增加不等于工期按比例减少。
- 分别保留原计划、当前预计和实际日期。重排时记录原因及影响，不能覆盖原计划来掩盖延期。
- 为高风险验证、集成和修复留出明确时间；多任务交付应写清功能冻结点和里程碑退出条件。缓冲按风险确定，不强制固定比例。
- 没有充分信息时给出条件估算或范围，不伪造精确日期。固定期限与范围冲突时，列出可后置范围或新日期，按用户已有授权决定；不得默默降低验收要求。

## 5. 状态与功能审查

沿用项目状态；没有约定时使用：待开始 → 已就绪 → 进行中 → 待审查 → 已完成，并支持阻塞、取消。

- 待开始：尚未满足全部开始条件；已就绪：具备开始条件但尚未执行。
- 待审查：实现及自检材料已提交，审查或集成尚未完成。
- 阻塞：记录具体原因、解除条件、处理负责人、下一步及原状态。解除后重新判定就绪条件。
- 已完成：约定交付物、验收、必要审查和集成均已完成，证据可定位。
- 取消或被替代：保留原因与替代 Task。已完成任务被重新打开时，保留原验收记录并说明失效原因。

在开发前把验收写成“前置条件／操作／预期结果”。按任务风险选择验证方式；界面任务检查实际画面与约定设计，数据或权限任务检查真实结果。Mock、静态检查、真实接口和生产验证分别标明。需要区分开发自检、测试与约定的产品确认时，分别记录类型、执行或判定者、被测版本、结论及证据；尚未完成的确认明确标为待完成。没有产品确认要求的小任务，不另设人工审批。

审查记录包含审查对象的版本、范围、方式、结论、问题及证据位置。自检不能冒充独立审查；未运行的检查不得标为通过。修复审查问题后验证受影响部分，旧截图或旧版本报告不能直接证明新版本通过。

每轮验证按以下指引收尾，沿用已有状态，不新增审批层：

| 当前结果 | 下一步与结束条件 |
|---|---|
| 约定交付、必需检查和确认齐备，无阻断项 | 按既定职责核对证据；仍需审查时记为待审查，满足完成定义后记为已完成。不默认重做全部测试。 |
| 技术检查通过，约定产品或外部确认未到 | 保存技术结论，记录确认负责人和解除条件，保留待审查或阻塞。没有影响结果的新变化时不因等待反复重测。 |
| 必需检查失败或环境无法验证 | 按既有预算修复并做受影响范围回归；到诊断界限后汇总证据，明确下一步，无法继续则记录阻塞。未通过项不得写成通过。 |
| 发现不影响本期交付的改进 | 在已有范围与延期权限内记录后置，不自动加入本轮必修项；安全、权限、数据正确性及约定必要检查仍须完成。 |

独立审查按用户要求、项目约定及实际风险安排。没有明确要求时，不把每次小修都拆成“委托修复 → 等待独立审查 → 再委托修复”的阻塞链；按既定分工修复并完成必要验证，在约定检查点汇总审查。明确要求的独立审查仍须完成，不能用自检代替。

“已完成”不自动等于“已部署”。交付计划要求部署时，单独记录部署版本、环境和部署后验证；部署本身也不能代替功能验收。

## 6. Git 与进度追溯

- 沿用项目提交规范，提交信息关联 Task 编号，如 `feat(T012): 支持预约改期`。一个 Task 可有多个提交；一次跨 Task 提交应列明涉及编号与原因。
- 实现、相关测试和文档按可审查范围一起提交，避免夹带无关改动。中途保存允许提交，但任务状态如实保留。
- Git 可用且本地提交已获授权时，在适当检查点提交；用户未授权执行或明确暂不提交时，提供拟提交范围并记录待提交状态。不要因为存在此规则擅自创建仓库、推送远端、合并或发布。
- 提交历史记录实现和计划的变化；任务记录保存计划、当前预计、实际时间、审查和阻塞。提交时间不能替代开工时间、验收时间或工时。
- 在提交创建后获取真实 SHA。当前提交无法在自身内容里记录自己的 SHA；可在后续进度提交中回填，或通过 Task 编号定位，不反复 amend 追逐自身 SHA。
- squash、rebase 或 cherry-pick 改变 SHA 后，保留最终目标分支中的对应记录。不要为了格式整齐重写共享历史。
- 适用集成要求的成果尚未进入约定目标分支或版本时，明确标记待集成；不能凭开发分支上的提交解除下游硬依赖。

## 7. 变更、阻塞与恢复

- 需求、接口或验收变化时记录来源、旧决定、新决定、受影响 Task、排期影响及处理结果；同步更新依赖与审查范围。
- 主流程阻塞时，主控优先处理解除阻塞所需工作；已获授权的独立支线可继续。若确实需要外部输入，准确记录等待条件，仅推进不争用现场的已就绪工作。需要评估时选择相关角色；专家人数遵循当前项目约定，模型及推理强度按“使用边界”中的规则确定。
- 对不确定故障，按风险设定一轮有界诊断：待区分假设、唯一变化、预期证据、运行预算与停止条件。同样输入且无信息增量时不重复实验、换现场或扩大矩阵；到界限后汇总已排除项与最小证据，由主控决定下一有依据的验证或记录外部阻塞。无法控制的依赖故障进入选型／范围决定，不把继续诊断当作必能完成的承诺。
- 每个实质检查点更新状态、证据、Git 关联和下一步。中断或交接前保存：当前任务、工作目录与分支、未提交改动、已做检查、阻塞、可启动任务和恢复动作。
- 用户要求暂停时，停止主控业务执行及自动续跑目标，向全部关联执行会话下达停工指令并核对状态；区分“指令已发送”与“已确认停止”，无法停止或确认时明确报告。仅做必要的安全收尾和快照，保留未提交成果与证据，不借收尾继续开发、提交或推送；不把暂停会话理解为关闭用户应用或共享服务。
- 暂停期间仅处理用户新授权的事项。调整计划或 skill 不代表恢复业务开发；用户明确恢复后，先核对现场与成果，再按新规则重新分工，旧派发指令不能自动重启。
- 分开记录用户恢复授权、主控实际执行、自动目标状态和各子会话状态。后续临时评审不撤销已有恢复授权；工具仍显示 paused 或子会话 idle 不能据此重复要求用户授权，也不能冒称它们已经运行。
- 恢复工作先核对实际文件、Git 状态和任务证据，不能只信任旧对话中的“已完成”。发现不一致时修正记录并说明原因。

## 交付前核对

确认本期需求都有去向，标为完成的需求有总体验收结论及证据；任务编号稳定、依赖无环、每项有负责人及验收标准、并行边界明确、估算包含必要验证与集成。实现和完成记录均有真实证据，适用时有 Git 对应关系。

报告本次交付、完成与未完成项、可立即启动的任务、阻塞及下一步。对计划文档的完成与业务功能的完成分别作出结论。
