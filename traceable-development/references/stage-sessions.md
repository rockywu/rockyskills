# 阶段会话模式

适用于用户明确要求：总控安排多个阶段，每个阶段由一个 Codex App 会话连续完成开发、测试、修复与阶段验收，再交回总控汇总。它是串行执行的可选模式，不替代普通单会话或隔离并行模式。按可独立验收的业务结果划分阶段，不为每个文件、测试步骤或修复轮次新建会话。

## 启用与角色

- 总控先记录用户已批准的阶段范围、指定检出目录与当前分支、允许的写入范围，以及创建阶段会话、派发任务和阶段向总控回报的授权。已覆盖本轮执行的授权不逐阶段重复询问；只要求讨论或修改 skill 时不启动阶段会话。采用本模式也不自动授权推送、部署、数据库或权限变更。
- **总控**是发起整个项目任务的会话，负责需求基线、唯一主计划、阶段准入、写入职责交接、跨阶段变更和最终签收。**阶段负责人**是当前阶段会话，在已授予的范围内承担本阶段的开发、问题分析、修复、测试组织和现场操作职责，不自行扩展范围、开启下一阶段或宣布整个项目完成。
- 实际执行指令写明角色、总控真实 ID、阶段 ID、执行轮次与创建后取得的阶段会话真实 ID，不笼统称双方为“主控”。创建请求尚无阶段会话 ID 时标为待登记，初始任务只允许只读核验并报告就绪，不授予写入权。这些是职责约定，不代表 App 原生存在父子关系、共享完整上下文、文件锁或自动调度器。
- 模型与推理强度遵循全局配置；未指定项继承总控的实际配置，不在本模式中固定模型。阶段会话的实际配置符合测试要求时可直接测试；不符合时由总控按全局规则安排同级测试执行者，阶段负责人仍组织验证并修复。测试执行者不得修改源码、配置、测试脚本或共享 Git 状态；缓存、报告等产物按下文的限定写入规则处理。
- 遵守全局委派层级限制。阶段会话不再创建下一层阶段会话或子代理；需要其他角色时向总控说明工作范围与资源，由总控在已有授权内安排。同级测试或专家不接管代码写入和共享现场。这一安排不能绕过规定的独立审查或产品确认。

## 同一分支的串行交接

“同一分支”在此指同一个本地检出目录中的当前分支，不是多个工作树同时检出同名分支。阶段准入时记录规范化目录、分支名和 HEAD，并在受控本地位置保存暂存、未暂存差异及相关未跟踪文件的可核对基线；敏感内容不进入消息、日志或仓库，必要时仅记录本地受保护快照的定位与摘要。只记 HEAD 不能代表已有未提交内容。重叠文件须保留原有修改并基于该基线核对本轮差异，无法归属或无法保护原内容时暂停写入。不得为了获得干净状态而擅自 reset、clean、stash、切分支或删除用户改动。

1. 总控先核对前置成果与阶段准入，确认前一负责人停止相关写入，再准备基线并创建只读待命的阶段会话。仅收到停止指令、会话空闲或超时不足以证明已停止，还须核对本任务的测试、构建等后台进程。
2. 阶段负责人先只读核对实际目录、分支、HEAD、已有改动与实际配置并回报就绪。总控取得真实会话 ID、核对就绪结果后，将阶段状态、当前写入负责人和执行轮次写入主计划，再停止自己的相关写入，并在已有用户消息授权内发送明确交接指令，附登记后的最新基线摘要。阶段负责人收到匹配真实 ID 和当前轮次的指令，重新核对该基线才可写入。目录不符、未知外来改动、交接消息不可用或无法确认其他写入者停止时保持只读并记录阻塞，不覆盖现场；自身等待结束不等于收到授权。
3. 阶段执行期间，总控和其他会话对该检出保持只读，包括主计划和 Git 索引；不得同时改代码、提交、切分支或启动会写该目录的检查。阶段负责人只写批准范围和指定阶段记录，不能修改总控主计划。确需项目内测试产物或变更当前范围时，按下文先交接再写入，不与阶段开发并发。总控可读取进度和接收变更，但消息本身不替代范围生效与写入交接。
4. 在开工、关键检查点及交接前核对分支、版本与改动范围，发现不符先停止相关写入并查明来源。共享索引、服务、账号和数据不会因会话分开而隔离；测试安排也须避免资源争用。
5. 阶段提交交付材料后停止代码和 Git 写入，确认本任务后台写入已停止，再将控制权交回总控。总控读回同一工作区并核对材料；需补修时优先复用原阶段会话，发起新执行轮次并重新交接，不与其同时修复。确不可续接且已确认停止写入时，才按全局替换规则和本文件的恢复要求登记新会话与新轮次；不能确认时保持阻塞。

这套交接记录不是技术互斥锁，不能约束其他未参与流程的会话或人工操作。无法确认独占条件时不继续写入；不能声称技能本身保证无冲突或无需恢复保护。

## 阶段内执行与证据

- 总控提供精简上下文：原始需求与已确认决定的位置、阶段目标和不做范围、相关 Task、已验收前置成果、验收标准、环境、权限、版本基线和未解决事项。不要复制全部历史，也不能只依赖上一会话的总结；阶段负责人先读取关联原始材料，不将缺失信息补成既定事实。
- 同一阶段会话依次完成：明确当前场景 → 开发 → 按全局配置测试 → 分析并修复问题 → 受影响范围回归 → 约定的阶段验收。测试预算、缺陷优先级、审查和产品确认要求遵循全局及项目规则；同阶段的修复与回归复用原阶段会话和适用的测试执行者，不重新分配到下一阶段。每轮结论按技能正文的验证收尾指引处理。
- 测试前明确执行者、被测范围、产物位置和资源需求，后续回归按受影响范围复用。缓存或报告优先禁用不必要写入或重定向到独立临时位置；工具只能写项目目录时，总控仅在已有用户授权内确认具体产物目录及运行边界。先确认阶段负责人及相关后台进程停止写入，再按交接规则将该检出中的写入临时限定为测试执行者生成获准产物；不得修改已跟踪文件或用户已有资产。测试结束后确认后台写入停止，基线源码、既有用户文件、Git 索引和分支未被测试修改，新增产物仅在获准范围内，再交回阶段负责人。授权不覆盖或无法限定副作用时记录阻塞，不能让配置不符者代跑充当合规测试。
- 需求变化影响当前目标、接口或验收条件时，先停止受影响的工作并保留用户指令来源；在最近的安全交接点确认该检出中的其他写入已停止，再交回总控更新主计划、依赖、基线和退出条件。总控以新执行轮次明确重新交接后，原阶段会话按新范围继续；此前既不按新范围写入，也不继续已受影响的旧工作。不影响本阶段的后续调整留到下一交接点记录，不因此暂停当前工作。
- 阶段记录保存内部 Task、实际操作和证据；主计划只保存阶段范围、授权、总体状态和签收，并链接阶段记录。同一字段只维护一处，总控在交接前后更新主计划，不在阶段执行中并发改写共享文件。
- 交付材料包括：阶段 ID 与执行轮次、完成和未完成项、实际修改范围、被测版本、检查结果及证据位置、已知风险、工作区状态和控制权交回确认。确有提交才写真实 SHA；没有提交时引用开工前的未提交内容基线及本轮差异、相关未跟踪文件清单与摘要，以便定位本轮被测状态，不为填 SHA 强行提交或暴露敏感内容。
- 测试、CI、合并、部署和实际业务验收分别说明。未运行、失败、阻塞和约定产品确认待办均不得写成通过。旧版本结果、截图和其他执行轮次的报告不能证明当前状态；阶段负责人不得凭自己写的总结宣称总控已签收。

## 回报、核验与下一阶段

- 完成约定工作后提交阶段交付材料，先记为“待审查”；阻塞报告不因此转为待审查或完成。若用户已授权阶段向总控发送回报，用真实总控 ID 发送一次精简通知，给出阶段、执行轮次、结果和材料位置；消息不是验收证据，也不自动保证总控正在运行。没有回报消息授权时保存材料，由总控读取；消息投递失败不重做阶段，也不据此标记签收。
- 总控优先使用 `wait_threads` 获取紧凑进度，必要时读取详情和本地证据。不得从会话 idle、最终文本、HTTP 成功或“我已完成”推断阶段已通过。读回目录、分支和实际版本，核对改动是否属于本阶段、测试是否对应当前成果、必需验收及已知缺陷是否满足退出条件。
- 核验聚焦阶段边界和必要证据，不默认重做整轮开发和全部测试；证据缺失、冲突或代码已变更时，要求补充或验证受影响范围。当前分支开发无需虚构合并提交或执行额外 merge，记录该分支中的真实成果及必要集成验证即可。
- 只有总控核验通过并确认上一写入者已停止，才把阶段标为“已完成”，解除相应依赖并进入下一阶段。若需要外部确认则保留待审查或阻塞。下一阶段进入时才创建其会话；同阶段补修优先复用原会话，不可用时按交接与恢复规则处理，较旧执行轮次的迟到回报不能覆盖当前状态或恢复写入权。
- 总控在当前执行回合内可继续已授权的阶段安排；跨回合无人值守运行须有实际可用且已授权的续跑机制。skill、完成通知和普通会话创建本身不提供永久后台调度，不为实现该模式擅自创建自动化。

## 创建、暂停与恢复

- 创建阶段会话前用 `list_projects` 确认准确项目，使用 `create_thread` 的本地项目环境，并传入精简上下文及“仅只读核验、等待交接”的初始任务；同一分支模式不自动创建工作树。项目路径必须对应指定检出，阶段会话开工前仍须自行读回验证。没有匹配项目或工具不能满足目录要求时，记录限制，不改用另一个目录冒充同一分支。
- 创建前按全局规则确定目标模型与推理强度，并遵守当前工具对参数的限制：仅在用户已明确指定具体模型且工具允许时传入模型参数；省略模型可能使用用户配置的默认模型，不能据此推断等于总控实际模型。用工具返回或可核实的运行配置确认实际值。无法取得目标配置、工具不支持所需配置或读回不符时，只读待命并报告限制，不将提示词当配置证明，也不将测试记为满足配置要求；不能擅自改用其他配置继续。
- 创建成功后登记真实 ID；得到创建结果或只读就绪回报都不等于写入已启动，须完成前述交接。失败不把计划写成已启动，不盲目重复创建。具体工具调用遵循[派发与结果记录](coordination.md)，不把主控在提示词中要求回报当作用户消息授权。
- 全部暂停时，总控通知当前阶段及相关测试角色，核对已停止与后台进程状态；未确认停止前不转交写入权。保留现场和未提交成果，仅做必要安全收尾。阶段负责人按[现场协作](onsite-coordination.md)保护登录态，不能擅自关闭用户应用。
- 恢复或替换会话前，先核对用户恢复授权、最新阶段与执行轮次、实际文件和写入者状态，再重新交接。总控改计划或修改 skill 不自动恢复阶段；主计划与实际状态不一致时先纠正记录。阶段会话不得自行恢复旧授权。

## 最小阶段记录

主计划按需增加以下登记表，其余细节放阶段卡；不重复普通 Task 的全部字段：

| 阶段 ID／目标 | 关联 Task／阶段卡 | 前置成果与退出条件 | 会话 ID／执行轮次 | 状态／当前写入负责人 | 交付材料／总控签收 |
|---|---|---|---|---|---|

```markdown
# Sxxx：阶段名称
- 角色：阶段负责人；总控 ID：
- 阶段会话 ID／执行轮次：
- 阶段目标、范围与关联需求／Task：
- 当前检出目录、分支、基线 HEAD 与已有未提交内容基线的受控位置：
- 允许写入范围、阶段记录位置、共享现场权限：
- 用户授权来源：创建／派发／写入／回报；超出范围仍需授权：
- 准入成果与退出条件；当前配置及测试执行者：
- 参考材料与已确认决定；待解决事项：
- 阶段结果、被测版本、实际检查与证据、未验证项：
- 本轮变更与工作区状态；后台写入停止及交回确认：
```

总控签收结论只写在主计划；阶段卡保留阶段方的实际报告。默认串行示例：总控准入 S001 → S001 会话执行及内部回归 → 停写交付 → 总控读回签收 → 准入并创建 S002。阶段卡不因子会话的自评自动变成整体项目完成。
